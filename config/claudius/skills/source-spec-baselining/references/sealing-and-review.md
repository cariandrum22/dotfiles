# 封緘・限定レビュー・採用

## 必要十分な検証を選ぶ

検査器には原典同一性、anchor、対象範囲の被覆、ID/参照整合、変更許容field、状態の非昇格など、実際に判定できることを担当させる。既存の読取専用検査や小さな再計算で足りるかを判断し、共通frameworkを毎回作り直さない。

検査器と生成器の一致は再現性の検査。双方が同じ作成者判断に依存することを開示する。生成器をimportしないことだけでも独立した意味検証にはならない。固定期待値の範囲、非guard field、検査器自身を束縛する外側manifestを明記する。

変異対照が必要なら、以下を守る。

1. 通常ケースを確認し、普通のbyteコピーか独立したcopy-on-write snapshotを作る。共有inodeをそのまま変更しない。
2. schemaを確認し、実際の変更をassertする。no-opや別recordへの変更を「検出した」と数えない。
3. 期待PASS/FAILと理由、観測した最初の拒否理由、変更前後hashを保存する。
4. digest門の先を試すrefreezeは私有fixtureに限定し、何を再pinしたか明記する。元packetへ戻さない。
5. 手前の門で正しく拒否された場合、後段の門が検証されたとは言わない。必要なら補完対照で到達させる。
6. 自由文の意味や有効ラベル間の交換が通るなら限界を記録する。全件PASSを意味の証明にしない。

欠落fileや不正座標を想定するCLIは、可能なら理由付きFAIL記録と非0終了を返す。module importの対照だけでCLIのエラー処理を試したとは申告しない。一時pathや時刻で出力が変わる場合はbyte再現する部分としない部分を分ける。

## 保存と実行の境界

必要な原典/旧記録を選択コピーし、元path/hashとコピー先/hashを対応させる方法を通常は優先する。offline可用性のために完全archiveが必要なら要求に合わせる。選択コピーを旧root全体の保持とは呼ばない。

- 旧packet/review/privateには書かない。hardlink共有inodeを変異テストや整形で変更しない。
- 新規保存は通常ファイルを基本にする。symlinkを残す場合、literal target、解決先内容、可搬性の各保証を分ける。
- reviewerのprivateコピー、巨大scratch、過去全packetの再帰コピーは必要な場合以外封入しない。必要容量と残置物の所有者を確認し、他者のscratchを無断削除しない。
- コピー除外の対象階層を明確にする。top-level logsの除外が継承入力内のlogs/manifestまで消さないよう、コピー後の厳密集合を比較する。
- 再生成/検査出力は新しい外部rootへ指定する。sealed root内へ書くCLIを拒否し、キャッシュ生成も考慮する。
- author-only scriptは自身のrootを明確に解決し、封緘済み/実行済みの再実行を拒否する。汎用の一時pointerで書込先を決めない。

秘密が入り得る取得header/logにはredaction方針と必要なスキャンを使う。スキャン0件は秘密不存在の数学的証明ではない。

## 封緘順序

ここでの封緘は改変検出可能なbyte集合の確定。OSの書込禁止、署名、外部タイムスタンプ、作成者認証が必要なら、それぞれ別の仕組みと権限で扱う。

1. 原典・判断・差分・依頼書、必要な検査器/再生成器を完成させる。元終了条件、判定対象、未調査を依頼書へ入れる。
2. 必要な検証を実行し、失敗と修正も開示する。意味判断を変えたら対応する照合/検査を更新する。無関係な全試験を繰り返さない。
3. 台帳更新が依頼範囲にある場合だけ、最終依頼/採用記録digestを束縛して追記する。beforeが前afterと一致し、after=before+appendであることを確認する。複数writerがあり得ればlockし、部分失敗後に無条件再試行しない。
4. 状態・report・検証結果を最終化する。相互hashの循環を避け、内部freezeと外部manifestの束縛対象を分ける。
5. 全対象ファイルのmanifestを作る。自己項目を除外し、そのdigestを外部receipt/信頼済み引渡しへ置く。除外pathは理由を明記する。
6. 新しい外部final-check rootでmanifest、対象ファイル集合（未登録/欠落）、必要な検査を実行する。前後のmanifest/digest一致を確認する。
7. 外部FINAL_RECEIPTにpacket manifest、依頼/採用記録、scope/state、検査器と結果のdigestを束縛する。必要ならfinal-check自身にもmanifestを作り、自己hashの循環を避ける。

封緘後の修正は新rootの差分として行う。前rootのfalse/pendingは履歴として保持する。台帳追記後の旧live検査失敗と旧packetのbyte不一致を区別し、liveの時点と新たな有効rootを示す。

## 判断可能なレビュー依頼

[依頼テンプレート](../assets/review-request.md)は関連項目だけ残す。同じ意味判断ができる原文、引用、作成者理由、差分、再実行方法を揃える。まだ判断できない抽象案への許可を先に求めない。

関係する場合には次を別結論として依頼する。

- 候補自体の忠実性と限定scopeの受理可否。
- 対象の文言/対応問題がこの候補で解決するか、閉鎖条件は何か。
- 元終了条件が満たされるか。採用条件付きなら条件と残工程は何か。

必須/情報所見、作成者関与、共有host/tool/operatorの限界を記録する。人間による規定の承認をAIセッション数で満たしたことにしない。依頼書作成と外部送信は別行為であり、送信権限を推定しない。

## 受領・採用・閉鎖

実レビューのdigestとscopeを照合し、verdict、必須/情報所見、条件付き結論を記録する。作成者期待値のreplayや過去レビューとの自己整合を独立レビューと呼ばない。

`accepted-in-scope` だけで全面受理しない。反対に、明示的に充足とされた元条件を、別工程の未読や任意改善のために未完了のままにしない。

採用が許可済みなら同一digestの候補を採用し、採用者・根拠・対象・状態遷移を新記録へ置く。審査後の編集上の改善を混ぜない。必要な変更は別候補へ回す。

文言問題の解決は実装適合、対象構成、provider契約検証の受理とは限らない。閉じる命題を限定する。残件は元条件に基づいて各工程へ割り当て、情報所見や任意案は指定状態を維持する。

採用の事務的記録だけを理由に新しい意味レビューを無条件に要求しない。元条件・権限・scopeが明確なら記録を完了させる。実質差分や未解決の阻害条件がある場合に次のレビューを組む。
